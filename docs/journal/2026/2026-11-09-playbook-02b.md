# 2026-11-09: Playbook 02b run

## Goal
Finish pve03 (storage, backups, template, k3s-03 VM), then grow k3s to three etcd servers behind kube-vip.

## What I did

### Step 1 - Quorum drill
Shut down pve03. With pve03 off: Expected votes 3, Total votes 2, Quorate Yes. After powering back on: Total votes 3, three green nodes in UI. Quorum survives one node down with no manual step, as ADR-0030 expected. [runbook-node-down](../../docs/domains/proxmox/runbook-node-down.md) already covers three nodes correctly.

### Step 2 - Storage and backup target
Restricted `usb-backup` to pve01,pve02, opened `backup-on-pve01` to pve03. Added pve03's address to `/etc/exports` on pve01. On pve03: `pvesm status` clean, `backup-on-pve01` active, usb-backup gone from its view, NFS mount writable.

### Step 3 - Wipe second NVMe and create nvme-data
Wiped nvme1n1, created LVM-Thin pool `nvme-data` (about 475 GB active), restricted to `nodes pve03`.

### Step 4 - Cloud-init template 9003 on pve03
Created `debian13-cloud` template (VM 9003) from `debian-13-genericcloud-amd64.qcow2` (2026-11-03), qemu-guest-agent installed, on `local-lvm`. `qm config 9003` confirms `template: 1`, `agent: enabled=1`, cloud-init drive.

### Step 5 - k3s-03 in OpenTofu
PR [homelab-infra#8](https://github.com/ssaav5-ai-labs/homelab-infra/pull/8): `variables.tf` adds `cores` (default 4) and `datastore` (default `local-lvm`) as optional per-VM fields. `main.tf` uses `each.value.cores` and `each.value.datastore` for the disk (cloud-init stays on `local-lvm`). `terraform.auto.tfvars.example` adds k3s-03: `pve03`, VM ID 103, 6 vCPU, 12288 MB, 100 GB on `nvme-data`, `192.168.86.213`, template 9003. Existing k3s-01 and k3s-02 are unchanged by the defaults.

🧑 User still needs to: add `k3s-03` to real `terraform.auto.tfvars`, run `tofu plan` (should show 1 to add, 0 to change, 0 to destroy), `tofu apply`, verify `ssh -i ~/.ssh/homelab debian@192.168.86.213 hostname`.

### Step 6 - Backup job for k3s-03
Backup job already existed: pve03, backup-on-pve01, 03:30, VM 103, snapshot, ZSTD, keep-daily 7, keep-weekly 4. Fixed [reference-proxmox](../../docs/domains/proxmox/reference-proxmox.md) and [runbook-backup-restore](../../docs/domains/proxmox/runbook-backup-restore.md): k3s-02 schedule corrected from 03:00 to 04:00. Ran backup: finished 12:38, USB disk 542 GB free.

### Step 7 - kube-vip and stable API address
PR [homelab-infra#9](https://github.com/ssaav5-ai-labs/homelab-infra/pull/9): `KUBE_VIP_VERSION=v1.3.1`, `K3S_API_VIP=192.168.86.210` in `versions.env`. Added `k3s/kube-vip/` (RBAC + DaemonSet template, ARP mode, eth0, control-plane affinity, leader election). `server.yaml.tmpl`: `tls-san` includes both `NODE_IP` and `K3S_API_VIP`. `agent.yaml.tmpl`: server URL uses VIP. `install.sh`: renders kube-vip manifests, deploys into server manifests dir; joining servers use VIP URL.

Saved etcd snapshot `before-ha` on k3s-01. `k3s/install.sh k3s-01` deployed kube-vip. Fixed env var names (`cp_enable` / `cp_namespace` instead of `vip_controlplane`). Verified: `kube-vip-ds` DaemonSet ready, leader elected (`k3s-01`), ARP broadcasting `192.168.86.210` on eth0. `curl -sk https://192.168.86.210:6443/livez` returns 401 (API answering on VIP, not a TLS error).

### Step 8 - Join k3s-03 as a server
PR [homelab-infra#10](https://github.com/ssaav5-ai-labs/homelab-infra/pull/10): added `k3s-03 server` to `nodes.conf`. First install attempt hit a cert SAN issue (k3s-01's cert lacked the VIP SAN before regenerating it). After deleting `serving-kube-apiserver.crt`/`.key`/`dynamic-cert.json` and restarting k3s-01, the cert included `192.168.86.210`. Second attempt failed because the first had already partially joined etcd (stale member at 192.168.86.213:2380 broke quorum). Restored etcd snapshot `before-ha` via `k3s server --cluster-reset --cluster-reset-restore-path=...`. Upon restart, k3s-03's pending retry joined successfully. Labelled `homelab.io/size=large`. Cluster now has 2 etcd members (no failure tolerance); must proceed to steps 9 and 10 in same sitting.

### Step 9 - Move stateful apps to k3s-03
Paused auto-sync on root, llm-gateway, and hermes. In homelab-gitops: NetworkPolicy fix (Hermes API egress to `192.168.86.213/32`) and an affinity PR (#57) switching Hermes, litellm, postgres, Argo CD controller/repo-server, alloy-singleton, and kube-state-metrics from node-specific to `preferredDuringScheduling` on `homelab.io/size=large`.

Postgres moved first (human step from a second shell: temporary nodeSelector to force the pod to k3s-03; old PV left as Released/Retain). Hermes moved next: set PV reclaim to `Retain`, scaled deployment to 0, took a safety tar of the data folder, deleted the PVC, synced to recreate it on k3s-03, copied data back, scaled up. Verified hermes/litellm/postgres all `Running` on k3s-03, Hermes answering on its API. k3s-01 memory dropped from ~87-95% to 62% (2054 Mi). Re-enabled auto-sync on all apps (root `prune: true, selfHeal: true` re-applied from `bootstrap/root.yaml` after the pause had left it `prune: false`).

### Step 10 - Rebuild k3s-02 as a server
Drained and deleted k3s-02 (no active volumes left; only DaemonSet/stateless pods). `tofu apply -replace='proxmox_virtual_environment_vm.k3s["k3s-02"]'` (plan showed 1 add, 0 change, 1 destroy). The clone completed but the provider's final read hung/crashed because the fresh cloud template lacks `qemu-guest-agent`; the VM was left running with no state. Recovered by `ssh-keygen -R 192.168.86.212`, installing `qemu-guest-agent`, then `tofu import pve02/102` and patching the empty `clone` block into state (else it forces replacement). Applied the in-place `scsi_hardware` change (`virtio-scsi-single`→`virtio-scsi-pci`, matching k3s-01/03; provider warns `iothread` is ignored on `virtio-scsi-pci`).

Ran `prepare-node.sh` (zram + swap), changed `nodes.conf` to `k3s-02 server`, ran `k3s/install.sh k3s-02`. Joined cleanly via the VIP — no etcd quorum issue this time. Verified 3 `control-plane,etcd` nodes, kube-vip DaemonSet 3/3, VIP answering, `/healthz/etcd` ok. Deleted the two old Released PVs (postgres + hermes) whose data had already been tarred off and whose disk was wiped in the rebuild. Cluster now has full single-node failure tolerance.

Re-ran it: `kubectl config view --minify` now shows `https://192.168.86.210:6443` and `kubectl get nodes` works through the VIP.
