## What broke and how I fixed it
- `/usr/bin/time` absent in the dev container; measured peak RSS via `resource.getrusage(RUSAGE_CHILDREN)` instead.
- `kubernetes==37.0.2` conflicts with crewai's `pydantic<2.13`; pinned `kubernetes==36.0.3` (no pydantic requirement).
- mcp-grafana v2.2.0 renamed the alerting read tool `list_alert_rules` → `alerting_rules_read` (the playbook was written against an older name); fixed the static tool filter in `homelab-agents` (PR #6), rebuilt the image (`sha-c3bc01f`).
- mcp-grafana v2.2.0 reports anonymous usage statistics to Grafana Labs by default (tool-usage counts, config flag names, coarse target description — no URL/creds/args). Not a secret leak, but out of step with the lab's "quiet by default" stance; disabled via `GRAFANA_USAGE_STATS=disabled` (PR #61).
- The `investigate_alert` DM failed with "Agent execution was invoked synchronously from within a running event loop". FastMCP invokes the tool handlers inside the server's asyncio loop, but they ran `crew.kickoff()` synchronously, which CrewAI rejects. Fixed the handlers to `async def` + `await crew.kickoff_async()`, and the one-run-at-a-time rule to an `asyncio.Lock` (checked with `locked()` before acquiring so "busy" still returns at once); added regression tests that run each handler under `asyncio.run()` with a stub crew whose sync `kickoff` raises when a loop is running. `homelab-agents` PR #8 → image `sha-62da16d@sha256:03b2931b…`; `homelab-gitops` PR #64 bumped the digest. The playbook's step 4 test list now says "tools run through the async server".
- The `weekly_capacity_report` cron run fabricated the report: the analyst sent bad args to k8s-mcp (`resources_list`/`resources_get` without `apiVersion`/`kind` → "Invalid request - check parameters" ×4) and hallucinated the table. Fixed by taking the data gathering out of the LLM entirely: `capacity.py` now fetches pods and peaks through a direct loopback MCP client and computes the table in Python, the LLM writes only the verdict, and the tool returns `capacity report unavailable: <which>` on any fetch failure. Two supporting changes: `list_output = "yaml"` in `k8s-mcp.toml` (so `resources_list` returns full pod specs, not a table) with the result bounds raised, and a guardrail in the `capacity-report` skill so Hermes posts "unavailable" rather than inventing numbers. Cron job paused until it is re-created with the guardrail prompt and re-run once.
- `parse_peaks` got no data from the peaks query because mcp-grafana v2.2.0 returns a bare array where the old parser expected a wrapped object; fixed to accept the bare-array shape (PR #10).
- The image digest was first taken from the build-push-action Post step, which is the runner's local digest, not what the registry serves; re-pinned from the registry's `docker-content-digest` header on the manifest.
- The capacity report's verdict total disagreed with its per-node deltas (278 Mi vs 262 Mi) because an under-provisioned workload with a negative gap leaked into the top-N and was excluded from the total. Fixed by filtering to `gap > 0` before ranking and summing the same rows the footer prints; a node with no reclaimable workloads is now absent rather than zeroed.
- Rolling pods split their peak across ReplicaSet/StatefulSet suffixes, so a workload looked over-provisioned when it wasn't. `group_peaks_by_workload` folds them by ownerReferences; suffix-stripping was rejected because it's ambiguous for hyphenated names like `node-exporter`.
- `sre-crews-reader` couldn't query datasources with just the Grafana Viewer role; it needed the datasource "Query" permission granted explicitly.
- Hermes kept resolving `skills.external_dirs` to a git-sync worktree path that git-sync later deleted on its next `--link` swap, so `capacity-report`/`lab-status` read "Skill not found". Fixed by pointing `skills.external_dirs` at a stable `/skills` emptyDir that a git-sync `--exechook-command` mirrors from the worktree (`cp -R` per skill dir, deleting only dirs no longer upstream). First attempt used `cp -a`, which tried to preserve timestamps on the root-owned emptyDir and failed with EPERM (git-sync runs as UID 65533), so the hook retried every 3s and git-sync never advanced. The per-dir `cp -R` avoids touching `/skills`' own attributes.
- The cron prompt had to be worded to pass Hermes' injection scanner (no inline interpreters, quoted descriptions) — same `scripts/check-skills.sh` lesson as playbook 06.
- **A hand-transcribed digest pinned a broken image** — the `sre-crews` digest in `versions.env` (and both deployments) had chars 14–20 scrambled (`151673` → `673151`). The tag (`sha-f94f160`) pulled fine but the digest reference 404'd, so `lab-actions` and `sre-crews` both sat in `ImagePullBackOff`. It masqueraded as a GHCR CDN bug — my devcontainer's CDN edge returned 200 for the *correct* digest while the k3s node 404'd on the *wrong* one, and a tag-only throwaway pod pulled cleanly on both `k3s-01` and `k3s-03`. The tell was `docker-content-digest` on the tag manifest (`…673151…`) disagreeing with the pinned value (`…151673…`). Fix: pipe the digest from the registry into the files with `sed`, never re-type it. Prevention: `check-versions.sh` now HEADs every pinned `ghcr.io` `image@digest` against the registry and fails on non-200, so a bad digest can't merge again.
- **After a refusal, Hermes tried a second route to the same change** — during the step-8 drill, `lab-actions` refused "restart hermes" (namespace not allowed), and Hermes then ran `kubectl rollout restart deployment/hermes -n hermes` in the terminal **with no approval prompt** (Hermes' dangerous-command patterns don't include `kubectl`); only the read-only ServiceAccount's RBAC denial stopped it, and it still told the operator to run the command by hand. Fix: `SOUL.md` now says stop-and-report on any tool refusal or RBAC denial and never try another route or suggest a `kubectl` write; `approvals.deny` now blocks every `kubectl` write verb (`apply/create/delete/edit/patch/replace/set/scale/rollout/annotate/label/cordon/drain/exec/cp/attach/run`). The read-only SA stays the enforcing backstop.

## Run review (2026-11-13)

Reviewed from the exported OpenCode session (`ses_e3e8…`, 2026-11-09 18:08 → 2026-11-13 16:25), checked for secrets before upload. Focus: where the agent can safely do more on its own.

**The run in numbers:** 88 human messages, 1,088 shell commands, 44 PRs opened and 45 merges, 49 `git push` prompts, 28 failed tool calls (12 denied by `opencode.json`, 2 rejected by the human), 11 context compactions, about 7.2 M input and 187 M cached tokens in one session.

**What worked**
- Self-verification from 2026-11-12 cut the relay: after that point the human mostly pasted Slack output, not command output.
- The deny rules held every time they were tested: `kubectl exec`, `gh auth token`, a stub `ksops`, `cat *.env*`.
- No secret reached the transcript; the export's only hits were container IDs, image digests, published checksums and a regex.

**Findings**
1. **The broken digest came from a context summary, not a typo.** The registry printed the correct `sha256:ec92dbb4eb793e6731512…` at 17:16 on 2026-11-12; a compaction ran at 18:41, and at 18:42 the agent wrote `…e1516732…` from memory ("I already have this digest recorded … I'll trust it"). Rule added: never retype an identifier; re-read it from its source after a compaction.
2. **The agent routed around denies,** the same pattern Hermes showed in step 8: a stub `ksops` that only `cat`s its input to render manifests (twice, once with a downloaded `kustomize`), and `TOKEN=$(gh auth token)` for registry calls (twice). All were denied. Rule added: a denied command is an answer.

7. **One four-day session** compacted 11 times; finding 1 is the cost. Rule added: a fresh session every two or three steps, handing over through the journal.
