### Step 5 (replacement, 2026-11-02): alert rules via a GitHub Action

Why: this Grafana Cloud stack is new, so it has **no data-source-managed alerting and no Cloud
Alertmanager**. Rules Alloy pushed to the Mimir ruler therefore could never notify, which is why
`PlaybookTest` never showed up in Grafana or Slack. Decided with Claude on 2026-11-02 to import the
same `PrometheusRule` manifests as **Grafana-managed** rules from CI instead.

- `platform/monitoring/chart-values.yaml`: turned off Alloy's rule sync (removed the destination
  `rules:` block and the metrics secret `extraConfig` on `alloy-singleton`). One owner for rules.
- New `.github/workflows/alert-rules.yaml`:
  - PR: `mimirtool rules lint` + `mimirtool rules check` (no token, no network).
  - Push to `main`: extract each `PrometheusRule` `.spec` with `yq` into a rule file with
    top-level `namespace: homelab`, then `mimirtool rules sync` through Grafana's Mimir-compatible
    convert API (`https://yellowhickory60.grafana.net/api/convert/`) with the data-source UID header
    `X-Grafana-Alerting-Datasource-UID=grafanacloud-prom`.
  - Pinned `yq` 4.54.1 and `mimirtool` 3.2.4 with SHA-256 verification; `actions/checkout` pinned by
    SHA; `permissions: contents: read`.
  - No `X-Disable-Provenance` (rules stay read-only in the UI on purpose) and no notification-settings
    header (the Grafana default policy already routes to the Slack contact point).
- The token is the `GRAFANA_RULES_TOKEN` GitHub Actions secret, created by Shawn; the agent never sees it.

Run notes for the review: **ADR-0021 needs an amendment: Grafana-managed rules imported from Git by
CI.** The original ADR said Alloy syncs `PrometheusRule`s to the cloud ruler; that no longer works on
new stacks. The trust model also changes: a CI token writes rules instead of the in-cluster Alloy token.

**Incident (same day), and the fix.** The first sync (PR #10, commit `193dc2a`) created
`homelab/playbook-test` but also **deleted 63 rule groups in a `knowledge-graph` namespace** we do not
manage (kube-prometheus/kubernetes-mixin group names such as `cpu.rules`, `node.rules`,
`kubernetes.alerts`). Cause: `mimirtool rules sync` mirrors the *whole* ruler unless scoped, so groups
not present in our files are deleted; the run doc's command had no namespace scope. Fix in
`fix/alert-rules-scope-namespace`: add `--namespaces=homelab` so the job only ever reconciles and
deletes within the `homelab` folder. **Action for Shawn:** check Grafana Cloud → Alerting → Alert
rules → `knowledge-graph` folder. If it held the Kubernetes Monitoring / Knowledge Graph mixin rules,
re-run that integration (or disable/re-enable it) to let it recreate them — do not re-sync this repo to
restore them. Lesson for the playbook: any `mimirtool rules sync` in CI must set `--namespaces`.
**Follow-up (same day): `LabSilent` and the extractor.** The `homelab` folder only had
`playbook-test`; `LabSilent` was missing. Searched the repo, every branch, the cluster
(`PrometheusRule/lab` had only `playbook-test`) and Grafana: `LabSilent` existed **nowhere** except
playbook step 6. Added it to `platform/monitoring/rules.yaml` as group `lab` per the playbook
(`absent_over_time(up{cluster="homelab"}[10m])` for 5m, critical). The extractor also only read the
first YAML document of files under `platform/monitoring`; it now scans the whole repo for every
`PrometheusRule` document (`yq eval-all`, multi-doc aware) and merges all groups into one
namespace-scoped file — `mimirtool` refuses multiple files sharing a namespace
(`repeated namespace attempted to be loaded`). PR #12; `--namespaces=homelab` kept.

**Step 5 verified (2026-11-02).** 🧑 `PlaybookTest` reached Slack, and `LabSilent` is `Normal` in the
`homelab` folder. Step 5 is done through the replacement path (Grafana-managed rules imported by CI from
Git); the original Alloy rule-sync path stays retired.

### Step 7: the gateway on the cluster (2026-11-03, 🧑)

Deployed LiteLLM `v1.106.6` as plain manifests in `platform/llm-gateway/` (PR #18): namespace,
ConfigMap (content-hashed), KSOPS-encrypted Secret, Deployment, Service, Ingress, ServiceMonitor, and
the `llm-gateway` Argo CD Application (prune + self-heal). Aliases `fast`/`code`/`reason` copied from the
workstation config (`local` left out), `callbacks: [langfuse_otel, prometheus]`, `master_key` from
`os.environ/LITELLM_MASTER_KEY`. Config holds no secret.

**Secret leak, rotation, and hardening.** The first `secret.enc.yaml` commit leaked the master key in
plaintext (a `data` value without an `ENC[...]` prefix — the repo is public). Rotated the OpenRouter key
twice and the master key (PRs #19, #20), fixed the encrypted file (PR #21), and hardened
`scripts/check-secrets.sh` to fail CI on any `*.enc.yaml` value that isn't `ENC[...]` or any line
containing `sk-or-`/`sk-lf-`.

**Metrics auth.** LiteLLM gates `/metrics/` behind the master key by default, so Alloy got `401` and
`up` was `0`. Set `litellm_settings.prometheus.require_auth_for_metrics_endpoint: false` (open-source
build) so Alloy scrapes unauth; the Ingress path is `/v1` (Prefix), so `/metrics/` is only reachable
in-cluster (PR #22).

**ServiceMonitor selector bug.** Alloy discovered the ServiceMonitor but generated **zero** scrape
targets: the selector matches Service *metadata* labels, and the Service had none (`app: litellm` was
only in `spec.selector`, which selects pods). Added the label to the Service (PR #23). Confirmed in the
Alloy debug UI the target `serviceMonitor/llm-gateway/litellm/0` → `10.42.1.50:4000/metrics/` is `up`.

**Verification.** `llm-gateway` Synced/Healthy; pod on k3s-02, memory **551 Mi** (requests 50m/384 Mi,
limit 1 Gi), start-up **~41 s** (17:10:59 → 17:11:40 ready). `/v1/models` and a real `fast` call work
